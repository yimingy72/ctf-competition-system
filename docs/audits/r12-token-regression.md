**通过：R12 的观测总 Token 增长约 100.8%，单位成功题成本增至约 2.12 倍。新增消耗主要集中在同题 Worker 的长探索与重复回合。** 校正任务归属后，lookup、drywell、vroom_vroom 三题贡献 97.73% 的净增长；这不是可节省比例。

## 2. Token 到底增加在哪里

### 2.1 总量与费用口径

模型请求按唯一 eventId 计数。SSE 工具分片按 choice/index 合并，用 tool_call_id 关联回执；请求历史中的旧工具调用不作为新调用。每个请求只采用一次最终可见 usage；缺 usage 保留未知。题目归属使用本 Worker 的当前 context，不能把 members 中别人的 assignment 或已释放的旧身份继承为当前任务。

| 指标 | R11 | R12 |
| --- | ---: | ---: |
| 唯一模型请求 | 2,337 | 3,510 |
| 有 usage / 缺 usage | 2,312 / 25 | 3,464 / 46 |
| 输入 Token | 319,400,378 | 642,748,560 |
| 输出 Token | 5,174,181 | 9,101,428 |
| 服务端 `usage.total_tokens` 合计 | 324,574,559 | 651,854,011 |
| 已报告缓存输入 | 304,176,525 | 603,713,450 |
| 已报告未缓存输入 | 15,223,853 | 39,034,343 |
| 缓存状态未知的已知输入 | 0 | 767 |
| 整轮观测总 Token / 成功题 | 17,082,872 | 36,214,112 |

净增长 **327,279,452** 可以不重叠地拆成：缓存输入 +299,536,925，已知未缓存输入 +23,810,490，缓存状态未知输入 +767，输出 +3,927,247，以及服务端 total 相对输入加输出的差额 +4,023。**输入占增长的 98.80%。** 缓存与未缓存 Token 不应按相同价格当作账单。

R12 存在三种原始口径：平台汇总 651,808,538；逐请求输入加输出 651,849,988；逐请求 `usage.total_tokens` 651,854,011。本轮采用最后一种，保留不同 provider 的计量差异，不重复把 reasoning 子字段加进输出。先前把没有缓存细分的 767 输入算作未缓存，得到 39,035,110；本轮改为已知未缓存 39,034,343，另列未知 767。

对有 usage 的请求做 `总量 = 数量 × 均次成本` 的对称算术分解：数量项占约 57.83%，均次项约 42.17%。这不是因果分摊；均次增加还包括更多请求落在高上下文难题上的题目构成变化。

## 3. 复核的完整挑战时间线与机制

### 3.1 lookup：更多高成本回合，没有得到最终成功

R11 有实际文件读取方向的阳性/阴性验证（L6289–6292）、候选复现（L6439–6444）和官方接受（L6467–6468）。R12 在 L4198/L4238 启动并取材料，14:29:31 起已有 Worker 请求，目标可连接。worker-23 在 L5988–5999 对错误类探针进行了有效纠正，说明增加成员并非全无价值。

R12 后续长期围绕没有闭合的执行链，以及“未找到 RCE”之类判断投入。导出中未见 R11 成功链关键 `WritableFile` 方向；不能因此断言完全没有尝试文件读取，更不能保证未核对镜像的情况下 R11 具体产物可以直接复用。

17:55:00.877 是请求暂缓，17:57:15.449 才是正式暂缓。78 个无新工具调用的收尾响应关联 28,836,618 Token，其中正式暂缓后只有 4 个，共 2,018,155，属于释放交接。**不能说已暂缓后仍被平台反复催解题。** 较窄的直接证据是 16 个纯自动 continue 触发后仍无工具的响应，共 7,656,199 Token；它们发生在解题或等待 Lead 决定期间。

批准修复：自动续跑额度不再因同行 Fact 改变整题 revision 而反复重开；提示词要求围绕裁判目标验证最短路径，并保留关键否定判断的便宜直接复核。没有增加事实评分器，不能承诺这些改动已经解出 lookup。

## 5. 历史输入的放大效应与不能乱删的部分

以下是原始请求正文累计 Unicode 字符，包含同一内容的反复发送，**不是 Token 或可节省账单**：

| 类别 | R11 | R12 |
| --- | ---: | ---: |
| 历史 reasoning_content | 660,923,121 | 1,295,627,138 |
| Bash 结果 | 204,394,597 | 431,826,053 |
| board_read 结果 | 33,604,584 | 69,673,034 |
| 用户通知 | 4,742,211 | 8,399,526 |

R12 历史 reasoning 占已统计正文字符约 64.82%，Bash 约 21.60%，黑板约 3.49%。因此优先减少没有必要的后续回合比只缩短几行通知更有意义。一次冗余回合会再次携带大量旧输入。

但当前 [DeepSeek Thinking Mode 官方协议](https://api-docs.deepseek.com/guides/thinking_mode/)（2026-11-23 核对）要求带 tools 的请求完整回传历史 reasoning_content，包括没有工具调用的 assistant 回合。缺失可能导致 400。**本轮没有删除历史 reasoning、禁用 thinking 或修改 provider 适配器。** 不能使用旧版本“新 user 到来可去掉旧 reasoning”的规则冒险修改当前协议。

同样，本轮没有批准换题清空会话：能由调用身份严格证明的跨题正文，R11 为 196 请求 / 4,731,825 字符，R12 为 78 / 3,089,996；lookup、drywell 没有观察到这一定义的跨题工具历史。该计数是下界，但不支持将跨题污染列为主要增长原因。

另外，R12 无 Lead/Worker 系统角色的直接模型 API 共 28 请求，27 个有 usage，总 238,399 Token，仅约 0.0366%。其中已有 26 个可联结到 Bash 外问。提示词补充不通过脚本直接请求其他模型，目的是保持现有同级 Worker 协作边界；不能把它包装为主要省 Token 措施。

大段会话/日志读取另有证据：符合日志读取且结果至少 10K 字符的 Bash 调用从 5 增至 23，正文历史回放从约 2.47M 增至 33.27M 字符。提示词改为从 Fact/Intent/证据文件获取协作信息，恢复或排错按调用/实体 ID 定位片段，避免整段日志再次进入模型。
