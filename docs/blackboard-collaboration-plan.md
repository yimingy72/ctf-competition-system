# 黑板协作收尾与纠错：方案、审查和实现

日期：2026-11-23。实施基线：`32461b2c4e6fdb3528a2663a21670ea446865d61`（PR #2 的合并提交，代码树与 `3b7ef50a1c4b1ed040a64d0402b9ff14c001c65d` 相同）。

本轮目标：让已有 Fact / Intent 协议在正常工具路径中更容易执行，并把已发生的状态变化完整传给同题成员。Lead 继续只负责准备、协调和审核；保留其本地工具入口。Worker 复用、闲置和领取任务的架构不变。

## 1. 真实轨迹支持的问题

原始来源：[competition-traces-r11-r12 Release](https://github.com/yimingy72/ctf-competition-system/releases/tag/competition-traces-r11-r12)。下列 R12 行号均指 `attempt-archive-01a201e3.ndjson` 的物理行；按 Worker、assignment 和工具调用 ID 回查，历史重带不计为新工具执行。

| 观察 | 证据 | 可以支持的结论 |
|---|---|---|
| 一项基础连通性验证已有成功 Fact，但对应 Intent 仍 open、没有结果关联 | R12 L9023 的完整任务快照 | 已有结果与工作状态没有收尾，不能据此直接计算重复实验或丢题损失 |
| 旧记录说某依赖不存在，后续记录已确认存在，却没有 disputes 关系 | 同一快照的 Fact、证据和争议字段 | 新成员需要自行比对矛盾；没有证据表明“最新一条”永远正确 |
| 新援助成员领取题目，但可见轨迹没有认领具体 Intent，随后调查涉及宽泛重叠方向 | Worker-9 同一 assignment 的调用，L9017–L10180 | 工作归属不够清楚；不能把每次实验都算为重复 |
| 一项新实验结果在正式 Fact 前被队友通过日志看到 | R12 L9173、L9195、L9268、L9281 | 存在短暂的共享窗口，但正式登记后更新确实进入队友请求 |

R11 L2996、R12 L9023 的实际模型输入已经要求“有效结果立即写 Fact”、发布方向和通过 resolves/result 收尾。因此，单纯重复添加口号不足以构成本轮修复。

R11/R12 的精确部署代码 ref 尚未完整映射。下面的代码缺口是在本轮固定实施基线上确认的，不宣称它们一定是 R12 相对 R11 回退的原因，也不量化尚未证实的解题收益。

## 2. 代码审查确认的两个接口缺口

### 2.1 快捷登记工具缺少已有协议字段

`src/coordinator.mjs` 中的 `record_fact` 原先只有 Fact 内容、来源、推论依据和 next_intents，没有顶层 disputes、resolves、result，也不转发这些字段。

普通 `board_act post_fact` 已实现这三项。最便捷的“刚得到 Bash 结果就记录”路径却不能同时关联反证或关闭方向，提示与工具能力不一致。

### 2.2 方向已关闭，但增量没有独立的 Intent 更新

`src/board.mjs::_fact` 原先已经修改 Intent 的 status、version、result 和 result_facts；`_postFactAction` 却只产生 fact.posted 和新方向的 intent.posted。

队友可以从 Fact.resolves/result 推断关闭，但增量消费者没有直接收到旧 Intent 的新状态。完整重读时数据正确，普通增量表达不完整。

Fact 争议关系的 task/entity/updates/通知投影已经存在，包括有界的 disputed_refs；本轮复用，不另建纠错索引或反证广播。

## 3. 批准并实施的方案

| 改动 | 机制 | 边界 |
|---|---|---|
| 补齐 record_fact | 增加可选顶层 disputes、resolves、result，原样传给 post_fact；result 使用既有 confirmed/rejected/inconclusive | Board 继续验证成对参数、同题引用和关闭权限 |
| 完整传播关闭状态 | 成功关闭后在同一 Board 事务、同一 revision 发 intent.closed；事件只带 intent_id，复用普通实体增量与通知批处理 | 不新增通知队列，不为每次关闭单独唤醒 Lead |
| 返回结果引用 | 关闭回执可选返回 resolved_intent；精简 Intent 更新和任务摘要保留 result_facts，任务摘要保留关闭结果；收尾 Fact 摘要保留 resolves/result | 普通 Fact 不增加 resolved_intent，不复制完整任务历史 |
| 明确 helper 的工作归属 | 在现有系统提示和 assignment_reason 中说明：复用自己当前持有方向，或认领 open 且依赖就绪的方向；独立新方向用 post_intent(claim:true) 写明目标、范围、方法、预期结果 | 允许必要短侦察，不为每个短命令建 Intent；恢复时先复用已有方向 |
| 明确收尾与反证动作 | 当前 holder 用 resolves/result；有新反证时填旧 Fact ID 的 disputes，并说明适用条件 | 争议不是平台判真；不自动关闭、删除旧记录或改派 |

### 已有结果如何收尾

1. **自己持有的方向已完成：** 在相关结果首次登记时，用 record_fact 或 post_fact 同时提交 resolves/result。
2. **无人持有、依赖就绪的 open 方向已经有足够证据：** 先按当前版本 claim_intent，再用 board_act post_fact 引用已有 Fact/Artifact 收尾。若结论是推论，使用 inference + derived_from。无需为了关闭状态重跑实验，也不应把最近一次无关 Bash 输出当作证据。
3. **方向由其他 Worker 持有：** 共享证据，由当前 holder 判断并收尾。新成员不能越过已有归属关闭它。
4. **只有中间进展：** 正常发布 Fact，保留尚未完成的 Intent。发布 Fact 不等于方向已经完成。

### 事务与重试边界

- post_fact 内的 Fact、争议修改、Intent 关闭、next_intents 和相应事件属于同一 Board 事务；后续字段失败会一起回滚。
- record_fact 仍先登记不可变 Artifact，再执行上述 Board 事务。后一事务失败可能留下未引用的 Artifact；不宣称两步整体原子。
- 相同 request_id、参数和身份下，Board 的 post_fact 重放不会重复关闭或增加事件。
- 不把上述保证扩大到任意重放整个 record_fact：该包装路径会重新登记 Artifact，新的 artifact_id 可能使同 callId 重放发生 request_conflict。这是既有两步包装边界，本轮没有另建重试状态机。
- 新字段可选，无数据库迁移；既有调用仍可使用。旧任务历史不会被扫描、补关系或重写，历史漏关方向仍需依据证据按正常协议收尾。

## 4. 独立方案审查与拒绝项

实施前分别完成了协议、通知与复杂度审查，批准上述最小方案。审查要求补充两点：只能认领 open 且依赖就绪的方向；复用旧证据应走 post_fact，不误用无关的最新 Bash 输出。实施后的独立 diff 复核无阻断问题，确认同 revision 的关闭事件不会被现有通知去重吞掉，普通闭环更新不会额外唤醒 Lead。

| 候选方案 | 审查结果 | 原因 |
|---|---|---|
| 每隔固定时间催写 Fact/Intent | 暂不批准 | 工具成功或时间流逝不能证明已有可复用结果，可能制造凑数记录和额外请求 |
| 每次 Bash 后强制提交 Fact、先登记才准用工具 | 拒绝 | 短侦察和中间失败不必形成独立协作记录，门禁可能阻塞合法推进 |
| 自动检测文本矛盾、把最新 Fact 判真 | 拒绝 | 条件、环境和证据强度需要判断，不能用新旧时间替代核验 |
| 自动关闭 open 或他人 claimed Intent | 拒绝 | 会改变工作归属，并把“看起来相关”误认为目标已完成 |
| 新 close_intent action、自动认领再收尾 | 不采用 | 现有 claim_intent + post_fact 足以表达有证据的收尾 |
| 全量扫描日志补关系、隐藏队列、复杂评分或自动改派 | 拒绝 | 已确认的问题可以在现有接口和事件路径修补，缺少引入这些机制的证据 |
| 扩大每次摘要为完整方法、证据和历史 | 不采用 | 已有 needs_task_read 与按实体读取路径；只补结果关系即可 |

这版保证的是：**模型提交关系字段时，工具能够传递、Board 能够校验、队友能够收到完成状态。** 它不保证模型一定及时登记、正确识别反证或选出独立方向，也没有实现持续的“漏写事实”语义检测。

## 5. 验证范围

必要验证覆盖：

- 一次 record_fact 登记证据、纠正旧 Fact、关闭自己方向并创建下一方向。
- 队友实际收到一个普通批量通知，包含新 Fact、关闭 Intent 及结果引用；不是仅检查数据库多了一条事件。
- open 方向须先认领；其他 holder、跨题引用、不完整参数、非法结果与旧任期证据继续被拒绝。
- 无效 next_intents 导致 Fact、争议、关闭状态和事件整体回滚；Artifact 的独立事务边界保持准确。
- 同请求的 post_fact 重放不重复增加结果、版本和事件。
- 原有分配摘要继续区分可认领、被占用、依赖未就绪的方向；恢复仍按现有身份与任务读取流程执行。

## 6. 后续真实轨迹验收

固定实际部署 commit，并沿用请求、Worker、assignment、环境代次和 tool_call_id 对齐。只用原始回执、实际提示和状态事件计算，不把 SSE 分片或历史回放算成新工具执行。

| 指标 | 口径 |
|---|---|
| 结果到 Fact 延迟 | 人工确认可复用结论的首次工具结果时间，到对应 Fact created_at；尚未发布单列，不能记作零 |
| Fact 到队友可见延迟 | Fact created_at 到相关队友第一个实际包含其实体正文的模型请求；区分发布、排队与消费 |
| 方向收尾 | 人工核对完成条件已有足够证据的方向中，仍 open/claimed 的比例及关闭延迟；中间进展不得当成已完成 |
| 反证关联 | 已核实存在条件相同或明确可比的矛盾案例中，新记录是否带正确 disputes；不按所有 Fact 数量作分母 |
| 援助方向归属 | 新 helper 明确持续调查目标后，是否认领现有方向或登记并认领有区别的新方向；短侦察不算违规 |
| 重复工作与成本 | 逐项核对实验目标、参数、证据和依赖；同时做共同题目配对比较与总体比较，并报告单位成功题 Token |

先观察上述最小修补后的剩余问题，再决定是否需要低频、基于明确状态的额外提示。Fact 数量、提醒次数或新增事件数上升，均不能单独作为优化成功证据。
