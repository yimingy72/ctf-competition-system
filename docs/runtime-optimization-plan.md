# R11/R12 轨迹审计后的运行时优化方案

## 证据边界

本轮实现基于 `e64b3db2a7cebdd0ef536cc752235122d472a2eb`。从审计指定的 R13 `4f4a97b2619b3f02fd0a8cb01b456a3f5042fe7a` 到该基线之间，仅 `competition-data/README.md` 和 `competition-data/manifest.json` 发生变化，运行时代码相同。原始数据的 attempt 身份、文件大小和 SHA-256 见 [competition-data](../competition-data/README.md) 及其 manifest；数据位于 [competition-traces-r11-r12 Release](https://github.com/yimingy72/ctf-competition-system/releases/tag/competition-traces-r11-r12)。

R11/R12 的运行代码 SHA 未得到可核验的完整映射。因此，轨迹可以证明当时发生的行为，固定 R13 代码与回归可以证明当前路径的机制，不能据此声称某项缺陷由 R12 引入，或某项 R13 改动在历史版本中不存在。本文记录落实的修复和后续验证，不将离线回归称为真实比赛提速或成功率提升。

## 设计原则

核心目标是在预算内获得更多被裁判接受的结果，同时降低每道成功题的时间和 Token 成本。需要减少的是无效重复、工具合同失败、已具备输入却无法执行的等待，以及失去证据后产生的错误决策。

Lead 完全不参与解题，保留本地工具供信息获取、环境准备、附件整理和运行故障处理。此边界由系统提示词明确约束；Worker 完成所有题目技术分析、计算和候选复现，Lead 检查已有证据并授权官方提交。工具入口保留的回归只证明能力可用和提示词已注入，不能证明真实模型必然遵守职责；这一点必须在后续真实轨迹中检查。

沿用现有 Board、事件通知、同级 Worker 池、会话恢复和官方回执对账。对已确认问题修复原有路径，不增加调度服务或新的持久化系统。

## 本轮批准并实现的改动

| 范围 | 证据支持的问题 | 最小实现 | 验证目标 |
| --- | --- | --- | --- |
| Lead 职责 | 轨迹存在 Lead 执行解题计算及复现、占用候选处理回合的行为 | 明确运维准备与题目求解边界；候选缺证据交回 Worker | 实际模型收到职责提示，Lead 仍能调用本地准备工具；真实比赛另查越界行为 |
| 工具合同 | 候选提交缺少版本被混为竞争；推论接口未透传依赖；错误细节丢失 | 补齐说明和 `derived_from`；区分非法参数与过期版本；回传脱敏诊断 | 模型和日志获得同一错误身份及修复信息，未知结果不重放 |
| Fact 复用 | 紧凑通知丢失推论种类与来源，容易把推测当已证事实 | 保留 `kind`、`provenance`、`derived_from`、环境代次 | 通知与原实体语义一致，`proposed` 不被提升为真 |
| 本地输入与远端实例 | 有本地材料的工作被远端名额挡住；首次启动与真实重开可能混淆 | 在现有 `arena_files` 增加显式 `prepare_paths`；复用 manifest；按代次记录是否实际 active | 选集缓存、配额失败和恢复后仍可派工；首次 active 保留 assignment；真实重开拒旧身份 |
| 文本读取 | SDK 文本读取先加载整文件，再截断返回值 | 通过公开 SDK 适配钩子按块扫描，仅保留有界文本 | offset、limit、长行、UTF-8、特殊路径、图片和取消仍有效 |
| 会话缓存 | 较早的 latest output 阻断已完成调用裁剪 | 保留独立 latest output 引用，近期完成记录恢复 200 条窗口 | 近期回放和 latest output 可用；未知调用和身份校验仍保留 |
| 异常进程收尾 | 取消后逃逸进程持有输出管道，阻塞工具返回 | 只对超时/取消的管道收尾设置 250 ms 宽限，并报告不确定性 | 三种取消路径及时返回；正常输出保留落盘和 backpressure |
| 决策输入 | 资源摘要缺少 Node/OOM/在途数量，通知缺少当前时间，重复调用被误述成无新结果 | 补少量已有采样字段、时钟及准确提醒；保留暂缓原因 | 摘要可追溯到来源，不根据未观测数据推断停滞 |
| 增员策略 | 增员义务容易把资源余量误当有效方向 | 删除主动增员义务，依据未覆盖新题、ready Intent 或具体 blocker 判断 | 不改现有数量上限，不新增评分；真实轨迹检查新增成员的独立产出 |

材料准备的 `ready` 只表示当前工作可执行。`prepare_paths` 不扫描或下载所有后续材料；单文件 `path` 保持纯下载，不隐式派工。远端验证仍由 Worker 确认环境实际为 `active`。没有足够真实材料时，保留缺料阻塞，不能靠字段变更制造可解条件。

## 对优化方案的二审

保留的新增状态只有每代次“实例是否实际 active 过”的布尔元数据，以及原有材料 marker 的准备范围；前者区分首次配额失败与真实实例重开，后者避免把一个选集误当全部离线附件。它们复用现有 SQLite 元数据与 manifest，不形成第二套调度状态机。

对缺少该历史标记的旧工作目录，已关闭或未知的实例采用保守判断，不推断它从未运行过；新运行与带标记的恢复才能准确保留首次启用前的本地执行身份。

保留的有界读取适配使用 SDK 公开接口，继续使用 SDK 的路径解析、访问和图片处理。其额外复杂度用于避免整文件驻留内存，并覆盖超长行；远处 offset 的扫描开销、图片内存开销和 SDK 内部会话历史仍需分别看待。200 条缓存修复也不等于 SDK 整段历史内存有界。

保留原有 unknown 对账、任务身份、环境代次和不可变证据检查。取消时关闭本端管道不等于所有进程已退出，不能自动重跑可能已经产生副作用的命令。

以下建议不进入本轮实现：

- 删除 Lead 工具入口或设置统一 Lead 命令时限：与保留环境准备能力的设计要求不符；本轮采用职责提示词。
- 新建隐藏任务队列、自动改派、独立分支评分或 Fact 自动裁决：没有证据表明它们是当前主要阻塞，且会叠加现有机制。
- 所有题目启动前必须全量下载、扫描或核验未来附件：会把后续材料变成当前步骤的不必要门禁。
- 单凭资源空闲自动扩 Worker，或把初始/最大 Worker 数直接调大：人数不等于独立方向，也可能放大资源竞争与重复上下文。
- 直接降低 600K 压缩阈值、按题换模型、重建恢复数据库或每题重置会话：现有证据不足以批准收益，且部分能力已有实现。
- 用离线测试、工具镜像检查或代码审查证明 R13 真实解题效果：这些验证的结论范围不同。

## 验证与发布

代码提交前运行 `npm test`，覆盖本地 HTTP 赛事、脚本化模型、实际 Pi SDK、Board 身份与回执、进程恢复以及新增缺陷回归。独立复核关注错误恢复、缓存回放、材料代次和提示词职责，不用只镜像实现的断言替代行为验证。提交记录和 PR 记录实际测试结果。

本轮本地验证：2026-11-23，Node.js 24.22.3，`npm test` **254/254 通过**，0 失败、0 跳过，耗时约 31.55 秒；`git diff --check` 通过。该测试集合包括原有 20 Worker 本地端到端流程及新增边界回归，不包含真实题目求解实验。

这次提交不构建或部署比赛镜像，也不调用真实赛事 API。后续真实验证使用测试过的不可变 commit 和构建出的镜像 digest；记录实际配置、输入资产 SHA-256、attempt 身份、模型参数和资源限制，再运行可比较的比赛样本。

## 后续真实比赛验证方案

1. **固定比较口径。** 同时报总体和共同题目配对结果；报告 accepted 题数、相同题目的解题时间、总 Token 与每 accepted 题 Token。取消、缺料未解和真实失败分别统计，未完成题不从总体资源成本中消失。不用完成更多题的总时长直接判断速度。
2. **按身份复算。** 模型请求按唯一 request identity 计算；工具按调用身份聚合 SSE 分片与重复字段，保留 assignment、worker、challenge、环境代次。每轮抽查至少 10 个模型请求、10 次工具调用，逐项回到原始记录。
3. **检查 Lead 行为。** 对每个候选记录提交到 Lead、证据检查和官方提交的时间；抽查全部 Lead 本地命令是否属于材料/运维准备。若仍出现求解或复现，先依据具体违规轨迹改提示，不预先上权限分类器。
4. **检查本地工作的真实收益。** 记录材料可用、派工、首次有效本地结果、远端 active、远端验证和 accepted 的时间；证明名额等待中发生了有效工作，不能把所有实例等待时间算成可节省时间。
5. **检查增员产出。** 对每次增员列出新增成员实际领取的任务/Intent、证据、结果及与已有方向的重叠。复用现有记录离线核对，不在运行时建立复杂评分系统。
6. **分开解释资源与模型延迟。** 记录 OOM 计数变化、Node 内存、在途请求/工具、API 请求耗时与工具耗时。缺少服务端 usage 的请求标为未知，不能把 SDK 默认零值算作零成本；同时报告 usage 覆盖率。模型请求耗时包含外部等待时，不将其全部称为模型执行。重叠区间按区间并集和关键路径计算，不相加为墙钟损失。
7. **验证每项根因。** 对进入排名的原因至少复核一条完整挑战时间线，复核最慢四题、少解题和取消题。把受影响请求成本与可避免成本分开；只有配对复测或可重放反事实支持时，才量化净节省。

先验证这一组确定性修复。跨题会话隔离和 Lead 推理等级只进入后续单变量实验：前者比较“稳定 Worker 身份、换题时新建会话、同题恢复继续旧会话”与当前复用策略，保留旧 journal 和未决结果；后者在职责边界落实后比较较低推理等级的候选响应与决策正确性。两者均不在本轮默认启用，也不引入动态模型路由或全量历史总结。

压缩阈值、Worker 数量和更强制的调度策略如需尝试，应分别提出可证伪的具体假设，并同时检查成功率、共同题目时间、每成功题成本及峰值资源，避免用单次总 Token 或离线吞吐替代解题效果。
